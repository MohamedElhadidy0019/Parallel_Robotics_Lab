Next-Best-View Scan Pipeline

A closed-loop system on a simulated UR5 + Robotiq-85: generate candidate camera views around a known object, filter for reachability, greedily pick the view that reveals the most unseen surface, move there with collision-aware planning, capture, repeat. No grasping.

Six pieces, one loop

How it's built, stage by stage

Each stage is independently testable and tied together by nbv_planner.py, driven end-to-end by full_pipeline.py.

A

Reachability cache

Sample a hemisphere shell of candidate camera poses around the object; IK-check each with CuRobo; cache reachable ones to disk. Computed once, not per run.

build_reachability_cache.pynbv_core/reachability.py
B

Known-CAD coverage

Sample 5,000 points + normals off the real mesh surface — the fixed checklist. Track which ones a real capture has confirmed seen.

nbv_core/coverage.py
C

GPU ray-scoring

For each reachable candidate, batched ray/triangle intersection (own Möller–Trumbore, PyTorch/CUDA) scores how many currently-unseen points it would reveal.

nbv_core/ray_scoring.py
D

NBV planner

Greedy argmax over A's candidates, scored by C, against B's live coverage state. Stops at target coverage or when nothing worthwhile remains.

nbv_planner.py
E

Motion execution

CuRobo MotionGen plans a collision-aware trajectory — self-collision and object/table collision — not a hand-rolled IK glide.

nbv_core/motion_planning.py
F

Orchestration

Wires A–E into the real scan loop. Captures a real depth image and backprojects it after every successful move.

Inside the loop

One iteration, three calls — decide, move, sense — repeated until coverage is high enough or nothing reachable is left worth visiting.

DECIDE select_next_view_pose() nbv_planner.py — greedy pick from the cached candidates, or None to stop
MOVE move_camera_to() nbv_core/motion_planning.py — CuRobo MotionGen plans + executes the trajectory
SENSE capture_and_backproject_view() full_pipeline.py — real depth capture → mustard-only filter → world-frame points
captured points feed back into the next DECIDE — coverage state updates before the next candidate is scored

What "decide" actually does — NBVPlanner.select_next()

  1. Fold any newly captured points into the coverage tracker (CoverageTracker.update())
  2. Stop and return None if coverage ≥ target
  3. Stop and return None if every reachable candidate has been tried
  4. GPU ray-score every untried candidate against the currently-unseen points
  5. Stop and return None if even the best score isn't worth a move
  6. Otherwise: mark the winner visited, return its pose

nbv_core/ray_scoring.py

How a candidate view gets scored

For every still-unseen point on the checklist, one candidate pose has to pass two independent checks before it counts as visible from there.

01

Front-facing

Angle between the point's own outward normal and the direction toward the camera must be small enough — is this bit of surface facing me, or facing away.

02

Not occluded

Fire a ray from the candidate straight at the point. If it hits the bottle's own body first, something else on the object is in the way — self-occlusion.

Σ

Score = count

Sum of currently-unseen points that pass both checks, per candidate. The candidate with the highest sum is the next move.

Design reference

Where this differs from the CUDA assignment

Same overall shape — known model, GPU visibility test, greedy pick — reimplemented against a continuous mesh instead of a voxel grid, since that's what a known-CAD assumption actually gives you.

PieceAssignment04This project
Known model Dense occupancy voxel grid Continuous mesh, sampled into 5,000 surface points + normals
Visibility test Ray marching — step along the ray, re-check the grid cell each step Exact ray/triangle intersection (Möller–Trumbore) — one closed-form solve, no stepping
"Already seen" test Exact voxel-index match — safe, since data is synthetic and noise-free Nearest-neighbor + 6mm threshold + normal check — real sensor points never land exactly on the checklist
GPU mechanism Hand-written .cu kernel Batched PyTorch tensor ops, dispatched to CUDA automatically
Loop structure One greedy step, demonstrated from every possible starting viewpoint One continuous sequence, iterated to convergence against a live, real coverage state

Open questions for the TA

Efficiency, not ceiling

Dynamic NBV needs more views than a fixed orbit for similar coverage

~42 successful views vs. ~16 for the same ~69–70% pre-base-exclusion ceiling. Likely cause: the occlusion test only ray-casts against the object's own mesh, not the arm/gripper — it can't predict when the real camera is blocked by the robot itself.

Known simplification

The scorer doesn't model camera field of view

Only position is scored, not orientation or FOV cone — works here because every candidate is pre-oriented to look straight at the object's center, and the object is small enough that this stays a close approximation.

Unresolved, worked around

Raw point cloud shows a registration artifact

Adjacent views don't perfectly align when viewed as a raw combined cloud. Root cause not fully isolated. Sidestepped by presenting coverage_visualization.ply — the known mesh colored by confirmed visibility — instead of raw points.

Scope boundary

Object pose is read directly from the simulator

A real deployment would need genuine 6D pose estimation (fiducial marker, ICP against the CAD model, or similar) to place the known mesh — this project gets it for free from PyBullet, since the object never actually needs to be found.
